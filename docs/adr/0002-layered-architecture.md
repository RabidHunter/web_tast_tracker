# 2. Шарова архітектура (Layered Architecture)

* **Статус:** Прийнято
* **Дата:** 2026-10-21

## Контекст
Для підтримання чистоти коду у модульному моноліті необхідно чітко розмежувати відповідальність різних файлів.

## Рішення
Код бекенду поділено на три строгі шари:
1. **`api/` (Presentation Layer / Controllers):** Приймає HTTP-запити, мапить їх у DTO, викликає сервісний шар та формує HTTP-відповідь. *Не містить бізнес-логіки.*
2. **`service/` (Application Layer / Use Cases):** Оркеструє виконання дій. Валідує логіку, керує транзакціями бази даних та мапить DTO у доменні моделі і навпаки. *Не знає про HTTP-запити.*
3. **`domain/` (Domain Layer):** Містить чисті сутності (Task) з їхніми інваріантами. 

## Напрямок залежностей
Залежності йдуть строго зверху вниз: `api` -> `service` -> `domain`. 

## Заборонені зв'язки
* Шар `api/` не має права напряму звертатися до бази даних (SQL-запитів) або до доменних моделей — він працює тільки через шар `service/`.
* Шар `domain/` не має жодних залежностей від інших шарів.
